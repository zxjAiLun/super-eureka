# D1.9.2 — External search-safety harness hardening

Status: **INFRASTRUCTURE COMPLETE — VALIDATION-ONLY, NO PROFILE PROMOTION**

## Scope

D1.9 added a versioned, external-to-the-search-code validation harness.
D1.9.1 added lifecycle, depth, and terminal hardening. D1.9.2 added the
absolute search deadline, bounded readers, PV assertions, and continuous-
output regression. The
manifest is a small project-curated CC0 corpus, not an Elo suite and not a
claim of broad tactical coverage. It is intentionally kept in the repository
so additions and removals are reviewable:

```text
tests/data/search_validation.epd
tests/search_validation.rs
```

Each entry records:

```text
id
category
full FEN
allowed best moves
expected score class
minimum depth
source
license
```

The initial corpus covers tactical captures, checking captures, mate
sequences, quiet and underpromotions, promotion races, en passant,
sacrifice/recapture context, stalemate, and KQK/KRK.

The test starts real UCI child processes and runs both:

```text
current
current-qsearch-pruning
```

The latter is exposed through the startup profile parser only for this
validation use. It remains a candidate profile and is not part of `Current`.

## Safety gate

For every case and profile the harness checks:

- UCI handshake identity;
- bounded UCI handshake, readiness, search, and quit/reap deadlines;
- process exit and `bestmove` completion;
- legal bestmove, including terminal `0000` semantics;
- allowed-bestmove membership when the case specifies one;
- expected mate/winning/non-losing/terminal score class;
- completed `info depth` at or above the manifest depth for non-terminal cases;
- score and PV captured from the highest completed depth;
- non-terminal PV is non-empty, starts with `bestmove`, and has a legal first move;
- unique manifest IDs and legal allowed-move sets;
- checkmate versus stalemate terminal classification.

Each engine has stdout and stderr reader threads backed by bounded 256-line
channels. A hung or malformed process is bounded by the following deadlines:

```text
uci / isready: 5 seconds each
fixed-depth search: 30 seconds
quit/reap: 5 seconds
```

On timeout or protocol failure the RAII process wrapper records recent stdout
and stderr, attempts `stop` and `quit`, then kills and waits for the child as a
last resort. This keeps a failed validation from hanging CI or leaving a
search process behind.

The `search_total_deadline_kills_continuous_info_engine` regression test uses a
controllable fake process that emits `info` forever without `bestmove`. It
verifies that the search deadline is absolute rather than being reset after
each output line, and that the fake child is killed and reaped.

It then rejects a candidate if its coarse score class is below the Current
baseline. PV equality and exact centipawn equality are deliberately not
required: a safe pruning candidate may choose a different equivalent move or
change a non-terminal score without losing the tactical result.

The gate is run with:

```text
cargo test --test search_validation
```

The v1 manifest has 12 cases. The main corpus test performs 24 independent
UCI searches (two profiles per case). The suite has three Rust test functions:
the manifest check, the 24-search corpus gate, and one controllable fake-
process deadline regression.

The category labels are coverage bookkeeping, not proof that each category is
solved exhaustively. In particular, the initial underpromotion case permits
all promotion pieces, and the en-passant/sacrifice cases use wildcard legal
moves with a coarse non-losing class. A future production gate must add pinned
unique-underpromotion, promotion-chain, x-ray, pinned-recapture, king-
recapture, and other SEE-specific cases with tighter expected results.

This is a validation gate only. It does not authorize `Current` changes,
SEE-pruning promotion, delta pruning, Elo/SPRT, or any new search feature.
The corpus must grow through separately reviewed, pinned cases before it can
serve as evidence for production promotion.
